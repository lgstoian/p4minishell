# P4MiniShell verification audit — 2026-11-21

This is a working audit document. It records the evidence found so far, the
false-green mechanisms, and the redesign plan. Nothing here is a hypothesis
presented as a fact; each item carries the command or file that produced it.

## 1. Evidence: the shipped gallery is wrong

`python tools/gallery_audit.py` on the tree tagged `v1.4.3` reports:

```
[FAIL] agenda.png: shows the shell prompt/keyboard, not an app page
[FAIL] aliases.png: shows the shell prompt/keyboard, not an app page
[FAIL] appl.png: ... (13 PNGs in total)
[FAIL] aliases.png and appl.png are the same screen (L1=1)
[FAIL] aliases.png and lib.png are the same screen (L1=4)
gallery_audit: 35 PNG(s), 13 shell capture(s), 3 duplicate pair(s)
```

Visual inspection of the named files:

| File | What it actually shows |
|---|---|
| `agenda.png`, `aliases.png`, `appl.png`, `control.png`, `hybrid.png`, `lib.png`, `memlog.png`, `moodsvc.png`, `pkgtest.png`, `svc.png`, `uitest.png`, `web.png`, `writer.png` | the shell transcript with BOUNCE frame echoes (`x=`, `y=`, `[M-BOUNCE-FRAME]`) and the prompt/keyboard row |

| `gfxtool.png` | canvas with title text overlapping the shapes and labels clipped |

All of them passed the gallery gate in the release sweep.

### Why this was a false green

`tools/suites/s25_apps_gallery.py` checks a capture with predicates equivalent to
"valid PNG + expected dimensions + >=1% ink + >=3 sampled colours". A shell
transcript dump satisfies all four. There is **no check that the right app is
on screen**, no check that the capture is fresh, and no check that two apps did
not publish the same pixels.

The captures are written directly into `docs/assets/apps/` by a normal test
run. A subsequent `git add -A` therefore commits them as documentation. This is
how the wrong images entered the release commit `9447f7f4`.

## 2. Audit findings

### False-green mechanisms (harness audit)

| # | Mechanism | Evidence |
|---|---|---|
| 1 | Every app-identity marker in the gallery was `c.note()`, never `c.check()`. A failed `launch` therefore published a screenshot of the shell as the app's PNG. | `tools/suites/s25_apps_gallery.py` (old lines 476-500, 519-522, 543-560) |

| 8 | None of `green_guard`, `verify.py`, `check_assets.py` ran in CI. | `.github/workflows/build.yml` |

### Batch apps (app audit)

- **No functional work / no page:** `aliases` (four echo lines), `appl` (a library routine), `pkgtest` (three echoes), `agenda`/`uitest` (commands echoed but results never checked). They were in the visual gallery despite having no screen.
- **Headless services with no page:** `svc`, `memlog`, `moodsvc`. Their stop markers were never asserted.
- **Real page, wrong capture:** `control`, `hybrid`, `writer`, `lib`, `web` (stream captured after exit), `snake` (one key then snap -> 3-cell stub).
- **Real rendering defect:** `gfxtool` drew sprite stamps *after* the title text, so balls covered both text lines. Its `:nofx` branch also emitted the success DONE marker.
- The apps were reached by `s14`/`s19`/`s23`/`s27`/`appdiff`; the false green was in *what was asserted*, not in a complete absence of tests.

### Runtime (harness timing audit)

- Boards run in parallel but suites are serial within a board: ~120 min wall = ~120 min of serial work per board.
- `boot()` cost ~15-20 s x 26 boots/board; `session.run()` paid a fixed `settle=0.5 + silence=1.2` (~1.7 s x ~1000 commands = 30-35 min/board).
- COM3 paid up to 120 s + 300 s Wi-Fi waits in `s17`/`s18` for legs that ended in `[note]` skips.
- `s14` and `s25` push the same 60-file app payload bundle; BOUNCE is launched four times per board.

## 3. Redesign principles

1. **Tests never write documentation.** Captures land in a staging directory;
   an explicit, separately reviewed command publishes them.
2. **A screenshot check must assert identity, not just non-blankness.** Every
   app declares its expected on-screen title/marker; the check queries the page
   model (`tui dump`) and the capture before accepting it.
3. **No duplicates.** Gallery PNGs are checked pairwise for near-identical
   pixels; a duplicate is a failure, never a pass.
4. **Freshness.** Each capture carries the app's own start marker and is taken
   after the app's first settled frame, not after a fixed sleep.
5. **No vacuous assertions.** A check that cannot fail on a broken product is a
   defect, not a pass; the static guard must catch tautologies and "marker seen
   in stale buffer" patterns.
6. **Speed without less coverage.** Replace fixed sleeps with marker waits, run
   boards/suites concurrently where safe, and stop re-running unrelated soaks
   for every change.

## 4. Acceptance criteria for the new harness

- `python tools/gallery_audit.py` exits 0 on the published gallery.
- Each app's staged capture contains the app's declared identity token, and
  pairwise signature distance exceeds the duplicate threshold.
- `python tools/harness/verify.py` includes the gallery-identity gate.
- A deliberately wrong capture (copy another app's PNG) fails the gate in a
  self-test — proving the guard can go red.
- A full two-board sweep completes in materially less time than 120 minutes
  with the same or greater assertion count.

## 5. v1.4.4 — tear-free partial presents on the DSI panels

**Defect.** `gfx show` invalidates only the dirty canvas rectangle, but LVGL's
flush writes that rectangle into the single scanned DSI framebuffer while the
panel may be reading it. A fast direction change (the ball hitting a wall) can
therefore show a one-frame tear. A full-frame refresh avoids it but drops the
reference board to ~15 fps, and a second full framebuffer costs 2.4/3.7 MB.

**Fix (implemented).**

- `managed_components/espressif__esp_lvgl_port/src/lvgl9/esp_lvgl_port_disp.c`
  now declares a weak, `IRAM_ATTR` hook `p4_gfx_panel_vsync_hook()` and adds
  `cbs.on_vsync` to the **same** `esp_lcd_dpi_panel_event_callbacks_t` used by
  LVGL's flush callback. A second registration call would replace LVGL's
  callbacks and stall every present; none is made. On ESP32-P4 the DPI bridge
  invokes `on_vsync` directly from the ISR, hence IRAM + internal RAM only.
- `components/command/gfx_commands.c` overrides the hook. For an integer
  upscale it stages the changed canvas rows (expanded to screen pixels) into a
  bounded internal-RAM back buffer (`width * changed_rows * 2`, capped at
  96 KB), skips the LVGL invalidation for that present, and the vsync hook
  copies the staged rows into the framebuffer plus an ISR-aware
  `esp_cache_msync` during blanking. A downscale or an oversized dirty rect
  falls back to the existing LVGL path, so rendering cost stays proportional
  to the sprite and BOUNCE keeps its 30 fps pacing.
- `tools/managed_patches.patch` / `tools/reapply_managed_patches.ps1` record
  the vendor change; the combined port hunk was validated to reconstruct the
  current source from pristine exactly.
- `tools/suites/s22_canvas.py` adds a bounce panel fixture: three colour-coded
  balls across a wall reversal, captured with `screenshot /panel`. It records
  checks for each ball, for no stale pixels in the reversal frames, for fully
  drawn (not half-written) balls, and for centroid motion right-then-left. No
  existing check was weakened.

**Verification status.** Both firmware profiles build with 0 errors and no new
C warnings (`idf.py -B build build` for jc1060p470c and
`idf.py -B build-tab5 -DP4_BOARD=m5stack_tab5 build` for m5stack_tab5).
`python -m py_compile tools/suites/s22_canvas.py` is clean. On-board s22, the
`gfx stats` pacing numbers (avg < 60 ms, dropped < 20) and a visual tear check
require hardware and remain with the hardware session.

classic 80x25 grid while callers put content at rows 5+, so prose/bars sat
outside the frame. Several apps also kept their content at authored 80x25 rows
